Page Annotations: Admin Settings (Wireframe 15 of 17)

Settings is the control panel for everything that affects the whole site. Changes here take effect immediately. Jean should understand what each section does before touching it. Plain English throughout.

Settings Navigation (left sidebar)

Seven sections organized in a sticky left-side navigation: Shipping Rates, Shipping Season, Restricted States, Plant Tabs, Shipping Policy Page, Mailchimp, and My Account. Clicking a nav item scrolls to that section. Each section has its own Save button so Jean can save one section without affecting others. This is safer than a single Save All button that could commit unintended changes across sections.

Decision needed: Should each section save independently (as shown), or should there be one Save All button at the bottom of the page? Independent saves are safer but require more clicks. A single Save All is simpler but risks Jean accidentally committing half-edited fields in other sections. Independent saves is the recommendation for a page this consequential.
Section 1: Shipping Rates

Two dollar-value fields: first plant rate and each additional plant rate. A live formula preview below the fields shows exactly what the current values mean in practice (example: 5 plants = $23.00). Jean can verify the math before saving. Changes here flow automatically to the cart, checkout, order summary, and order confirmation pages. The Shipping Information page rate table also updates automatically when these values are saved here, resolving the sync problem flagged in Wireframe 08.

Business rule: Shipping rates are read from the Settings table at runtime by every page that displays or calculates shipping. There is no hard-coded rate anywhere in the codebase. This is how Jean can update prices without developer involvement.
Section 2: Shipping Season

Spring open and close dates, and fall open and close dates. These appear on the Shipping Information page automatically when saved. Fall dates can be left blank if Jean does not ship in the fall. This resolves the content gap flagged in Wireframe 08 where shipping season dates were placeholders Jean had to update manually.

Content needed at launch: Jean must enter her actual spring and fall shipping dates before the site goes live. These fields will be blank until she fills them in.
Section 3: Restricted States

Two chip-based lists: blocked states (red chips, hard stop at checkout) and flagged states (amber chips, notice required). Jean can add states using the dropdown and Add button, and remove them by clicking the X on each chip. Changes here flow automatically to the checkout page notice logic and to the Shipping Information page state restriction section. Adding a state to blocked or flagged does not require any code change.

Business rule: Blocked and flagged state lists in the Settings table are the single source of truth for the checkout restriction logic. Changing them here updates the checkout behavior immediately on the next page load. Decision needed: Should Jean be prevented from removing all blocked states or all flagged states entirely? An empty blocked list would mean no states are blocked, which may or may not be Jean's intention if she clears all chips accidentally. A warning like "Are you sure you want to remove all blocked states?" would prevent accidental clearing.
Section 4: Plant Category Tabs

Four toggles, one per plant type: Daylilies, Iris, Lilies, Other Perennials. Daylilies is on at launch; the others are off. When Jean toggles a tab on, it immediately appears in the public site navigation. When she toggles it off, it disappears. This is the mechanism described throughout the wireframes for controlling which tabs customers see.

Business rule: An inactive tab hides all plants of that type from the public catalog regardless of their individual active status. Jean should only activate a tab when she has plants of that type ready to sell with photos uploaded.
Section 5: Shipping Policy Page Content

Two editable text areas: the "When We Ship" body text and the "Caring for Your Plants" body text. These correspond to the editable sections of the public Shipping Information page. The rate table, state restriction callouts, and sidebar all update automatically from their own settings sections; Jean does not need to manually update those here. A preview link opens the live Shipping Information page in a new tab so Jean can verify her edits before saving.

Decision needed: This wireframe shows two separate text areas for the two most likely editable sections. Should more sections of the Shipping Information page be editable here (e.g., the Questions section at the bottom), or are these two sufficient? Jean should indicate how much she expects to change that page over time.
Section 6: Mailchimp Integration

Two fields: the Mailchimp API key and the Audience/List ID. The API key is masked by default with a Show button to reveal it. A connection status indicator shows whether the current key is valid and which Mailchimp audience is connected. The Save button doubles as a connection test: saving attempts to connect and reports success or failure. Jean needs to set this up once at launch; after that she should not need to touch it unless she regenerates her Mailchimp API key.

Content needed at launch: Jean must obtain her Mailchimp API key and Audience ID and enter them here. Edward can walk her through finding these in her Mailchimp account during the launch setup session.
Section 7: My Account

Login email address and password change fields. The email shown is dazzlingdaylilies@yahoo.com, which Jean has confirmed as her preferred contact. Password change requires entering the new password twice to confirm. Leaving both password fields blank saves the email change only, not the password. This is the only place Jean can update her admin login credentials without developer help.

Decision needed: Should the login email and the "from" address for outgoing transactional emails be the same field, or separate? Right now the transactional email from-address (the address customers see in their confirmation email) is configured in the server .env file. If Jean wants to change it later, that currently requires developer access. Adding a "From email address" field here would give her control over it. Worth discussing during the build.
