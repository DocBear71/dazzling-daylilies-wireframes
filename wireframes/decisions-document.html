1 Navigation and Site Structure WF01, WF02, WF03c
D-001 Inactive plant-type tabs: grayed-out vs. hidden entirely at launch Jean to decide

At launch only the Daylilies tab is active. The wireframes show Iris, Lilies, and Other Perennials grayed out with a "(coming soon)" note. The alternative is to hide them entirely until Jean activates them.

  • Option A (shown in wireframes): Grayed-out tabs with "(coming soon)." Signals to customers that more categories are coming, builds anticipation.
  • Option B (recommendation): Hidden entirely. Cleaner at launch; no risk of customers clicking a non-functional tab. Tabs appear automatically when Jean turns them on in Settings.
WF01, WF02, all public pages
D-002 Bundles tab name: confirmed as "Collections" Decided — committed

The standalone bundle catalog page uses the tab label "Bundles." Jean may prefer a different name that better fits her brand voice.

  • "Bundles" — direct and clear, used in wireframes as default
  • "Collections" — warmer, more editorial
  • "Garden Collections" — most descriptive but longer
  • "Plant Sets" — functional, no ambiguity
  • Recommendation: Jean decides. Whatever she picks becomes the tab label, the page heading, and the term used throughout the admin guide.
Committed: Jean confirmed "Collections" as the tab label on May 23, 2026. All wireframes, the index page, and the admin Settings toggle should use "Collections." The URL remains /bundles unless Jean requests otherwise.

The Bundles tab should be added to the Plant Tabs section of the Admin Settings page (WF15) as a fifth toggle, alongside the existing four plant-type tabs. It should default to off and Jean turns it on once at least one bundle is configured and ready to sell.

2 Catalog and Plant Browsing WF02, WF03
D-004 Catalog grid: 3 columns vs. 4 columns Jean to decide

The catalog page (WF02) uses 3 columns. The homepage featured plants (WF01) uses 4 columns. The difference is intentional: 3 columns leaves more room for the short description text on each catalog card, making browsing easier. But the inconsistency may feel odd.

  • Option A (recommendation): 3 columns on catalog, 4 on homepage. Different purpose, different density is acceptable.
  • Option B: Match both at 3 columns for consistency.
  • Option C: Match both at 4 columns. Cards feel smaller but more plants per view.
WF02, WF01
D-005 Plants per page in the catalog Jean to decide

WF02 shows 12 plants per page. PlantFans shows everything on one page (no pagination). Jean should decide based on how her customers prefer to browse and how large her catalog will grow.

  • 12 per page: Fast load, manageable per page, more clicking.
  • 24 per page: Good balance, two pages for a 48-plant catalog.
  • All on one page: Matches PlantFans; no pagination friction. Heavier mobile load as catalog grows.
  • Recommendation: 24 per page at launch, with an option to increase later. Revisit when Jean knows her final catalog size.
WF02
D-006 Catalog search scope: name only vs. broader fields Jean to decide

The search box on the catalog page currently matches plant names only. Broader search could include color, hybridizer, or description text.

  • Name only (recommendation): Predictable results. Most customers search by variety name.
  • Name and hybridizer: Useful for experienced collectors searching by breeder.
  • All fields: Most flexible but can produce surprising results.
WF02
D-007 Filter option counts in the sidebar Jean to decide

WF02 shows counts next to each filter option (e.g., "Orange / Gold (11)"). These update as other filters are applied, showing how many plants remain in each category. Useful but adds development complexity.

Recommendation: Include counts. They meaningfully improve the browsing experience, especially for customers trying to narrow a large catalog. The Livewire reactive query that drives the filters makes dynamic counts feasible without major extra work.
WF02
D-008 Sold-out plants: show in catalog and on homepage vs. hide Jean to decide

This question applies to both the homepage featured plants grid (WF01) and the full catalog (WF02). Showing sold-out plants with a badge lets customers see the full range and contact Jean if interested. Hiding them keeps the catalog to purchasable items only.

  • Show with badge (recommendation): Honest, keeps catalog full, allows customer interest signals to Jean.
  • Hide: Cleaner, no "why can't I buy this?" questions. Requires Jean to remember to re-activate when restocked.
WF01, WF02
D-009 Plant detail photo aspect ratio Jean to decide

WF03 shows the main plant photo as a square (1:1). Portrait ratio (3:4 or 4:5) may better showcase tall scape shots. This affects how Jean should frame her photos.

Recommendation: Ask Jean what aspect ratio her photos tend to be. If she shoots in landscape or square, 1:1 is fine. If she has many tall scape shots, 3:4 is better. The catalog card thumbnails remain square regardless; only the large detail-page image changes.
WF03
D-010 Quantity selector: allow multiples vs. max 1 per plant Jean to decide

The plant detail page (WF03) and cart (WF04) show a quantity selector allowing more than 1 of the same plant. If Jean sells only one fan per customer per variety, the selector can be removed entirely, simplifying both pages.

WF03, WF04
D-011 Coordinated flowers: bidirectional vs. one-directional relationships Jean to decide

When Jean pairs Plant A with Plant B in the Plant Editor, Plant B does not automatically show Plant A as a companion. Jean must set both directions manually. Automatic bidirectional would save Jean effort but reduces her control over which pairings appear on which pages.

  • One-directional (recommendation for launch): Simpler to build, Jean has full control. Document clearly in admin guide.
  • Bidirectional: More convenient for Jean. Slightly more complex data model and query logic.
WF03, WF11

D-011b Plant attribute abbreviation system and display order: confirmed Decided — committed

Jean confirmed the abbreviated attribute display format for the plant detail page on May 23, 2026. Rather than a full attribute table, each plant shows a compact single-line abbreviation string. The confirmed abbreviations and their display order are:

Display order: Bloom Size • Foliage (Dor/Ev/Sev) • Genetics (Dip/Tet) • Bloom Season (EE/E/EM/M/ML/L/VL) • Fragrant (FR) • Special Forms (Dbl/Spider/UFO/Poly/Noc) • Rebloomer (Re) • Scape Height

Example: 5.5" Dor Tet M FR Re 28"

A customer-facing abbreviation key is also confirmed as a required UI element on the plant detail page. Implementation options: tooltip on hover over each abbreviation, or a collapsible "What do these mean?" section. To be finalized in the design phase.

Fan size (DF = Double Fan, SF = Single Fan) is always stated on each listing. Customers can order multiple fans of the same variety using the quantity selector.

Committed: Abbreviated single-line attribute display replaces the full attribute table on the plant detail page. The plant editor stores full field values; the abbreviated display is rendered from those stored values. The plant_type, color, bloom_size, ploidy, foliage, bloom_time, rebloomer, and fragrant database columns remain unchanged. A ships_as field (DF or SF) is added to the plants table.
WF03 all variants, WF11, plants table schema
D-012 Bundle discount type: fixed dollar amount only, no percentage Decided — committed

Jean sets a bundle price in the Plant Editor. The wireframes show the discount as both a dollar amount ("Save $12.00") and a percentage ("9.7% off"), calculated automatically from the bundle price vs. individual total. Jean needs to decide which format she wants shown to customers.

  • Dollar amount only: "Save $12.00." Concrete, easy to understand.
  • Percentage only: "Save 10%." More impressive on large bundles.
  • Both (recommendation): "Save $12.00 (9.7% off)." Gives customers the most information. Easy to implement since both are calculated automatically.
WF03 revised, WF03b, WF03c, WF11 revised
D-013 Bundle price entry: Jean enters bundle price directly vs. enters a discount rule Jean to decide

In WF11 (revised), Jean types the bundle price as a single dollar amount (e.g., $112.00). The system calculates and shows the savings automatically. The alternative is for Jean to enter a discount percentage (e.g., 10% off) and let the system calculate the bundle price.

  • Jean enters bundle price directly (recommendation): More control. Jean decides exactly what she wants to charge.
  • Jean enters a percentage: Simpler mental model. Consistent discount across all bundles if Jean uses the same rate.
WF11 revised
D-014 Mix-and-match bundles vs. fixed bundles only Decided — fixed only at launch

Bundles are fixed sets designed by Jean. Customers cannot swap individual plants within a bundle. Mix-and-match configurator functionality is explicitly out of scope for the initial build.

Committed: Fixed bundles only at launch. Mix-and-match may be considered as a future feature after launch if Jean requests it.
WF03b, WF03c, WF11 revised
D-015 Bundle cart behavior: line items vs. single bundle line Build note

When a customer adds a bundle to the cart, each plant in the set needs to appear as a line item. The bundle price needs to be allocated across those line items for the order sheet and order records to make sense. Two approaches:

  • Option A (recommendation): Each plant appears as a separate line item at a proportionally discounted price. A "Bundle: Jean's Sunset Garden Collection" label groups them visually in the cart. Order sheet and order records are clean and itemized.
  • Option B: A single "Bundle" line item at the bundle price, with the plant list shown as sub-items. Simpler visually but complicates the order sheet thumbnail requirement and the order record schema.
WF04, WF05, WF06, WF16
D-016 Bundle photo strip on the bundles catalog page: cap at 5 photos with +N more indicator Decided — committed

For 7 and 9-plant bundles, showing all photos as narrow slivers in the card photo strip looks visually awkward. Capping at 5 visible photos with a "+N more" indicator keeps all cards consistent.

Recommendation: Cap at 5 photos for all bundles larger than 5 plants. Show a "+N more" indicator on the last sliver. This is the standard pattern used by similar multi-image components across the web.
WF03c
D-017 Bundle availability when a component plant is sold out Open — needs a decision

If any plant in a bundle is sold out, the bundle cannot be sold as a complete set. The question is whether this is handled automatically or manually by Jean.

  • Automatic (recommendation): Bundle is marked unavailable automatically when any component is sold out. Shows a "Currently unavailable" message on the card. Reactivates automatically when all components are back in stock.
  • Manual: Jean toggles the bundle off herself. More control, more administrative overhead.
WF03, WF03b, WF03c
4 Checkout and Payments WF05
D-018 Flagged-state notice copy: Jean must approve exact wording Jean to decide

The notice shown to TX, AZ, and FL customers at checkout says Jean will "contact you before shipping to confirm your order can be fulfilled." This is a commitment Jean is making in writing to every customer from those states. The exact wording must be approved by Jean before the build.

WF05, WF08
D-018b California: hard-blocked, not flagged (updated from original wireframes) Decided — committed

An earlier version of the wireframes incorrectly placed California in the flagged-state (notice) group alongside Texas, Arizona, and Florida. The signed contract and working instructions are unambiguous: California is a hard-blocked state. Customers with a California shipping address cannot complete checkout. They see the same hard-block message as Hawaii, Alaska, Puerto Rico, and US territories.

The flagged-state notice (agricultural compliance popup) applies only to Texas, Arizona, and Florida. California customers receive no notice and cannot proceed regardless of whether they acknowledge anything.

Committed: California is in restricted_states_blocked alongside HI, AK, and PR. The Settings default is ["CA","HI","AK","PR"]. California is never in restricted_states_flagged. All wireframes, flow diagrams, and this document have been updated to reflect this. The RestrictedStateChecker service class unit tests must explicitly verify that California returns a blocked result, not a flagged result.
WF05, WF08, WF15, Flow Diagram 01, RestrictedStateChecker service
D-019 Order summary panel: sticky vs. scrolls with page Open — needs a decision

On the checkout page (WF05), the order summary sidebar is shown as sticky (stays in view as the customer scrolls through the long form). This is the standard modern e-commerce behavior and is shown as the default in the wireframe.

Recommendation: Sticky sidebar. Keeps the total visible while the customer fills in their address and payment details. Reduces "wait, how much am I paying?" uncertainty at the moment of clicking Place Order.
WF05
D-019b Local pickup option at checkout: confirmed and in scope Decided — committed

Jean confirmed on May 23, 2026 that she wants to offer local pickup at her Fairfax, Iowa address as an alternative to shipping. Customers pay online and select pickup at checkout. No shipping charge applies to pickup orders.

This adds the following to the build scope (absorbed, not a change order per Edward's decision):

Checkout: a "Shipping or Local Pickup?" toggle before the address section. Selecting pickup hides shipping address fields, shows pickup instructions, and zeroes out shipping cost. Order confirmation email: different text for pickup orders ("Jean will contact you to arrange a pickup time"). Order status page: "Ready for Pickup" status instead of "Shipped." Admin order list: visual indicator distinguishing pickup from shipped orders. Order sheet: "LOCAL PICKUP" label so Jean does not accidentally pack and ship a pickup order.

Committed: Local pickup is absorbed into scope. Wireframes WF05 (Checkout), WF06 (Order Confirmation), WF07 (Order Status), WF14 (Order Detail), and WF16 (Order Sheet) all need pickup-specific variations added. The orders table needs a fulfillment_type column (shipped/pickup). The settings table needs a pickup_address field for the instructions shown at checkout.
WF05, WF06, WF07, WF14, WF16, orders table schema
D-020 Order number format: DD-YYYY-NNNN vs. alternatives Jean to decide

Order numbers use the format DD-2027-0042 (prefix, year, four-digit sequence). This resets to 0001 at the start of each calendar year. Once orders start coming in, changing the format is disruptive. Jean must confirm this format before launch.

5 Order Status and Fulfillment WF07, WF14
D-021 Four-step status tracker: include "Delivered" step or end at "Shipped" Jean to decide

WF07 shows a four-step tracker: Received, Processing, Shipped, Delivered. The system has no way to automatically detect delivery. Delivered would only show if Jean manually marks it, which she is unlikely to do routinely.

  • Three steps (recommendation): Received, Processing, Shipped. Ends at the last state Jean actually controls. Customers use the USPS tracking number for delivery updates.
  • Four steps: Include Delivered but accept it will rarely be used.
WF07
D-022 USPS tracking button: carrier-specific vs. generic copy Jean to decide

WF07 shows a "Track on USPS" button once a tracking number is entered. If Jean ever switches carriers, this label is wrong. The safer approach is a generic "Track Package" button or simply displaying the tracking number as plain text for the customer to copy.

Recommendation: Display the tracking number as plain text with a "Copy" button. No carrier-specific link. Future-proof and requires no code change if Jean switches from USPS to UPS or FedEx.
WF07
D-023 Mark as Shipped: require tracking number first vs. allow without Open — needs a decision

Should the "Mark as Shipped" button in WF14 be disabled until a tracking number is entered, or can Jean mark an order shipped without one?

Recommendation: Require tracking number before allowing Mark as Shipped. An order showing "Shipped" on the customer's Order Status page with no tracking number creates confusion and support emails. The small friction cost for Jean is worth preventing that customer experience.
WF14
D-024 Add "Mark as Refunded" button to Order Detail Build note

WF14 does not include a "Mark as Refunded" button. Without it, orders that Jean refunds through Square will permanently show as "Paid" in the admin. This creates end-of-season reconciliation confusion.

Committed addition: Add a "Mark as Refunded" button to the Order Detail sidebar that updates the payment_status field to 'refunded' without processing any money movement. No separate wireframe needed; this is a one-button addition to WF14.
WF14
6 Admin: Plants and Photos WF10, WF11, WF12
D-025 Active toggle in plants list: immediate vs. with confirmation Jean to decide

Flipping the Active toggle on a plant row in WF10 takes effect immediately with no confirmation dialog. The change is reversible with a second click. Jean should confirm she is comfortable with immediate-effect toggles.

Recommendation: Immediate, no confirmation. Toggling is fast and reversible. A confirmation dialog on every toggle flip would slow Jean down significantly during end-of-season bulk changes.
WF10
D-026 Admin plants list: plants per page Jean to decide

WF10 shows 15 plants per page. With 48 plants that is 4 pages. Jean may prefer a higher count or "show all" since she is managing her own catalog and likely wants to see everything at once.

Recommendation: 25 per page, or offer a "Show all" toggle that Jean can use when she wants the full list. At 48 plants "show all" is perfectly performant.
WF10
D-027 Dropdown values: fixed list vs. Jean-configurable from Settings Jean to decide

The attribute dropdowns in WF11 (Color, Bloom Size, Ploidy, etc.) have a fixed set of values seeded into the database at launch. If Jean needs a new color category or bloom time label, that currently requires a developer change.

  • Fixed list (recommendation for launch): Simpler to build, sufficient for a 48-plant catalog. Document the values clearly in the admin guide.
  • Configurable from Settings: More flexible as catalog grows. Adds meaningful complexity to the Settings page and requires careful validation to prevent malformed data.
WF11
D-028 Photo upload: unmatched photos auto-discarded vs. save blocked Jean to decide

In WF12, when Jean clicks "Confirm and Save," any photo she has not manually assigned to a plant is discarded automatically. The alternative is to block saving until every unmatched photo is either assigned or explicitly discarded.

  • Auto-discard (recommendation): Faster for Jean on large batches where a few unmatched photos are common. The summary bar clearly shows the count of unmatched photos before she saves.
  • Block save: Safer, forces Jean to address every photo. More friction on large uploads.
WF12
D-029 Photo upload max file size and count Build note

WF12 shows limits of 100 photos per batch and 20 MB per file. WebP conversion on Hostinger shared hosting must be queued via the Laravel scheduler, not processed inline, to avoid request timeouts on large batches. Jean should not close the browser during upload but can log out after: conversion runs in the background.

Committed: Photo conversion is queued as a background job using the database queue driver. The scheduler cron processes the queue. Upload UI shows a "conversion in progress" state. Photos appear on the plant detail page once conversion completes.
WF12
7 Admin: Settings WF15
D-030 Settings save behavior: per-section vs. single Save All Decided — per-section saves

Each section of the Settings page has its own Save button. Jean saves Shipping Rates independently of Restricted States, etc. This prevents accidentally committing half-edited fields from other sections.

Committed: Per-section saves. This is the safer pattern for a settings page with consequential fields.
WF15
D-031 Shipping rates on the Shipping Information page: static text vs. dynamic from Settings Decided — dynamic from Settings

The Shipping Information page (WF08) displays shipping rates and state restriction lists. These pull dynamically from the Settings table, the same source the cart and checkout use. There is no separate text for Jean to update manually; changing the rates in Settings updates the Shipping Information page automatically.

Committed: Shipping rates and state restriction lists on WF08 are rendered dynamically from the Settings table. Jean updates them once, in one place.
WF08, WF15
D-032 Transactional email from-address: in Settings vs. .env only Open — needs a decision

Currently, the from-address for outgoing order confirmation emails is set in the server .env file, requiring developer access to change. Jean may want to update this herself (e.g., if she gets a custom domain email later).

Recommendation: Add a "From email address" field to the My Account section of the Settings page. Low development cost, meaningful long-term convenience for Jean.
WF15
D-033 Season total definition on Dashboard and Orders List Jean to decide

The Dashboard (WF09) and Orders List (WF13) both show a "season total" order count and revenue. What constitutes a "season" needs a definition Jean agrees with: calendar year, or the shipping season window defined in Settings?

D-034 Order sheet generation: HTML with print CSS vs. DomPDF Decided — HTML with print CSS at launch

The order sheet (WF16) is a browser-printable HTML page using CSS print media queries. No PDF library needed at launch. Jean can print to paper or use "Save as PDF" from her browser's print dialog.

Committed: HTML with print CSS for launch. DomPDF can be added later if Jean wants to save and archive order sheets as PDF files.
WF16
D-035 Thank-you note and care reminder text on order sheet: editable from Settings Open — needs a decision

The thank-you note and care reminder strip at the bottom of the order sheet (WF16) are currently static text. Jean may want to update them seasonally without developer involvement.

Recommendation: Add both as editable text fields in the Settings page (WF15), alongside the existing Shipping Policy text fields. Low development cost, removes Jean's dependency on Edward for seasonal copy updates.
WF16, WF15
D-036 Shipping label: Jean's label printer type Jean to decide

The shipping label (WF17) is formatted for 4 x 6 inch labels. The admin guide print setup instructions will differ depending on whether Jean uses a thermal label printer (Dymo, Rollo, MUNBYN) or prints label sheets on her existing inkjet or laser printer.

WF17
D-037 Postage: system-generated USPS barcode vs. Jean handles externally Decided — Jean handles postage externally

The shipping label generated by this system is an addressing label only, not a postage label. Jean purchases postage separately through USPS Click-N-Ship, Pirateship, or a similar service and affixes it to the package alongside the addressing label.

Committed: No USPS API or postage integration at launch. USPS barcode integration is meaningful added scope and cost. Jean almost certainly already has a method for purchasing postage.

10 Database Schema Changes from Bundle Addition WF03 revised, WF03b, WF03c, WF11 revised

The bundle feature requires additions to the existing database schema defined in the working instructions. These changes do not affect any existing tables; they only add columns to the plant_coordinations table.

Table Column Type Purpose
plant_coordinations bundle_enabled boolean, default false Controls whether the bundle panel appears on the public plant detail page and on the Bundles catalog page.
plant_coordinations bundle_price_cents integer, nullable Jean's bundle price in cents. Null when bundle_enabled is false.
plant_coordinations bundle_name string, nullable Optional human-friendly name (e.g., "Jean's Sunset Garden Collection"). Defaults to "[N]-Plant Collection" if null.
plant_coordinations bundle_description text, nullable Jean's explanation of why these plants go together. Shown at the top of the bundle detail page (WF03b).

A new migration file (add_bundle_fields_to_plant_coordinations_table) covers all four columns. No existing migration files need to be modified. The bundle-related Eloquent queries, the BundleController (or equivalent), and the /bundles route need to be added to the standard Laravel structure during the build phase.
